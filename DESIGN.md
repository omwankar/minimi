# Design

Minimi is a chat agent with one capability, web search, and a memory of what this user already asked. The questions it has to get right name an earlier day and then ask whether that answer is still true. The shape of the system follows from that, and from doing it in one cheap model call.

Dates are resolved in code, in the user's timezone, before the model sees the message. "3 November", "Monday", and "last Tuesday" become calendar days. "Last Tuesday" keeps two candidates, the latest Tuesday and the one before it, because the phrase is used both ways. Recall then keeps notes from those days only, and if both days have notes it keeps the one that shares the topic of the question. "Still correct today" is a check against now, not a request for today's transcript. If Monday is named and there is no note, the agent says so and does not guess a shortlist. Memory is a JSON ledger of turns, entities, and the claims the agent asserted (a price, a plan, a launch), written after every reply. No embeddings. These questions name a day and a subject, so a day index plus word overlap is the right index, and it costs nothing.

Search runs only when the live web can change the answer. "What did I ask?" does not search. A price or launch check searches each remembered product once — `HubSpot pricing and latest product updates`, not the user's whole paragraph — at most five queries, in parallel, cached on disk for three hours. DuckDuckGo is the default, so search is free. Brave or Tavily are optional upgrades, chosen only when a key is set. For the top hit of each query the server fetches the page and keeps a short extract around the price, because the number lives in the page, not in the snippet. The model does not drive a browser and is not given a second tool.

One DeepSeek call writes the reply. The model is `deepseek-flash` with thinking forced off. Thinking is on by default and is billed as output; it is the expensive part, and it is the wrong default once the old claims and the new pages are already in the prompt. The system prompt does not include the date, so it stays byte-for-byte stable and DeepSeek's prefix cache hits after the first turn. Context is the matching notes (the stored claims, not the whole old answer), a short page extract, and nothing else. The live thread is sent only when no note was recalled, so a dated question is not billed twice and is not mixed with today. The reply streams. A trailing memory block is cut off before the user sees it and stored as topics, entities, and claims. That block is what makes the next "has it changed?" possible. If the model forgets the block, product names are taken from the text so the ledger still works.

When the user is checking an old answer, the reply starts with a verdict: still correct, changed, partly changed, not in memory, or could not verify. A price change is written as before → after, with the earlier date and a source for the new figure.

## Rejected

An open tool loop. It is slow, it wanders, and it pays for a model round-trip per search. Replaying the full transcript. It costs more and mixes days together. Embeddings and a hosted vector store. The wrong index for "what did I ask on 3 November", and another bill. A browser agent. The task allows one tool, and a pricing page can be read with a plain fetch. Leaving DeepSeek thinking on, or using the pro model. Stronger on puzzles, wasteful when the job is to compare a stored claim with a page. A search provider's built-in answer API. It hides the query, ignores "since Monday", and bills per query the model decides to run.

## With another week

A frozen check of these three question shapes against a seeded ledger, run on every change. A small price parser that diffs the stored claim against the fetched page in code, so the verdict is not only the model's. Thinking turned on, at low effort, only for "is this still true?" turns. Brave as the production search backend when a key is present, with DuckDuckGo kept as the free fallback.
